# Fixtures and golden data (WP-06)

Test inputs for the analysis engine, and the expected outputs the engine must
reproduce. The build plan's testing strategy is in
[docs/PLAN.md §5](../docs/PLAN.md#5-testing-strategy); this directory is how it
is wired.

```
fixtures/
  fixtures.json        the manifest: every fixture, what trap it exercises, what to expect
  synthetic/*.jsonl    crafted sessions, one trap each          (scripts/build-synthetic-fixtures.ts)
  adversarial/*.jsonl  hostile or non-session inputs            (same script)
  captured/<name>/     real Claude Code sessions, content-scrubbed (scripts/scrub-capture.py)
  golden/*.json        expected output per fixture              (tools/refsim/refsim.py emit)
  generated/           the 100MB parser stress fixture — built at test time, git-ignored
```

## How the pieces fit

1. **Fixtures** are session logs. Synthetic ones are generated by a script so
   they are reviewable as code; captured ones are real sessions with every
   conversation payload replaced by a placeholder (see *Scrubbing* below).
2. **Goldens** are produced by the Python reference simulator in
   [`tools/refsim/`](../tools/refsim/) — an independently written second
   implementation of the parser, cost engine and counterfactual model. One
   golden per fixture, named `<fixture id with / → __>.json`.
3. **The harness** `src/engine/golden.test.ts` runs the TypeScript engine over
   every fixture and compares with its golden, field by field, with a
   floating-point tolerance of 1e-10 on dollar figures (the two
   implementations sum in different orders; any real disagreement is orders
   of magnitude larger). It also enforces, per fixture:
   - the **format-drift canary**: the Claude Code `version` a fixture carries
     must be inside `VALIDATED_VERSION_RANGE` (`src/engine/contract.ts`),
     except the one fixture marked `canaryExempt`, which must take the
     warn-don't-fail path instead;
   - the **content-poison property**: the marker `POISON` planted in every
     conversation payload never appears in the parser output, the analysis, or
     the golden;
   - the **reconciliation property**: replaying at the observed TTL reproduces
     the actual cost (exact for every bucket except a 5m-dominant bucket that
     also carries 1h writes — a mid-session config flip, where the "5m"
     scenario deliberately reprices the flipped writes);
   - **manifest completeness**: every `.jsonl` under `fixtures/` is listed.
4. **CI** runs the reference sim's own hand-computed tests and
   `refsim.py check`, which re-derives every golden and fails on any byte of
   difference — so a golden can never drift from the sim that owns it.

Neither implementation is the oracle. When they disagree, the number is worked
out by hand and the side that is wrong gets fixed; goldens are never edited to
make a test pass.

## Commands

```sh
npm run fixtures:build   # regenerate synthetic/ and adversarial/ from the script
npm run golden:emit      # (re)write every golden from the reference sim
npm run golden:check     # verify the committed goldens are current (CI)
npm run test:refsim      # the reference sim's own unit tests
npm test                 # includes the golden harness
```

Adding a fixture: drop the `.jsonl` in place (or add a case to
`scripts/build-synthetic-fixtures.ts`), list it in `fixtures.json` with a
`trap` and an `expect`, run `npm run golden:emit`, then check that the golden
says what `expect` claims before committing.

## Synthetic fixtures

Each entry in `fixtures.json` names the trap from the feasibility doc / plan
it exercises and the behavior the golden should show. Rows mirror real
v2.1.251 logs: `user → attachment → assistant` chains, one assistant row per
content block with the full usage on each, realistic `usage` subfields.
Timestamps start at `2026-08-30T12:00:00Z`; prices are Opus 5 unless the trap
is about models.

The adversarial set covers the validation rules in
[docs/PLAN.md §2](../docs/PLAN.md#input-validation-and-secure-file-handling):
a non-session JSONL, malformed lines above and below the rejection ratio,
hostile metadata strings (control characters, ANSI, bidi overrides, markup,
2000-character values), prototype-pollution keys, and invalid numerics. The
one input class not committed is the multi-hundred-MB single line; that is
covered by `src/engine/parser.test.ts` and `parser.large.test.ts` at test
time, because a fixture that size does not belong in git.

## Captured sessions

Real sessions, scrubbed. Each directory carries a `capture.json` with the
source Claude Code version, counts, and scrub-rule version.

| Capture | What it is | Why it matters |
|---|---|---|
| `captured/parallel-subagents/` | A v2.1.251 session from building this repo: 126 main-thread requests plus **27 subagent transcripts** under `subagents/` (parallel, and nested to spawn depth 2). Main ran at 1h, subagents at 5m. | The modern separate-file layout (contract F2): the main file yields only a `main` bucket; each agent file yields only a `subagent` bucket. 1h wins the main bucket ($68.91 vs $90.31 at 5m, 4 expiries). |
| `captured/scenarios/tight-loop-5m/` | Claude-enacted: eight back-to-back prompts on a toy project with `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` (13 requests, largest gap 18s). | The 5m-configured capture the plan asked for. 5m wins ($0.406 vs $0.473); no expiries in either scenario. |
| `captured/scenarios/gap-heavy-1h/` | Four prompts at 1h separated by 6m / 8m / 12m of idle time (9 requests). | The shortening direction on real data: the 5m scenario adds three expiries; 1h wins ($0.32 vs $0.70). |
| `captured/scenarios/gap-heavy-5m/` | The same prompts and gaps with the TTL set to 5m (8 requests). | The lapse-heavy path on real data — and a **partial-invalidation** finding, below. 5m wins narrowly ($0.562 vs $0.579). |
| `captured/scenarios/model-switch/` | Two turns on Opus 5, `/model` to Sonnet 5, then effort high → medium, all at 1h (10 requests). | Two hard resets (`model-change`, `effort-change`) that no elapsed time explains; per-request pricing across two models. |

The scenarios were recorded by `scripts/capture-scenarios.sh`, which drives
`claude -p` in one throwaway directory per scenario (the cache is scoped to
machine + directory, so scenarios must not share one) with read-only tools,
then scrubbed like any other capture. They double as the app's bundled
samples: `scripts/sync-samples.ts` copies them to `public/samples/` and
derives `index.json` (title, description, expected verdict) from each
capture's `capture.json` and golden, and the harness asserts the copies are
byte-identical.

### Finding: partial invalidation, live

`gap-heavy-5m` shows what feasibility §7 predicted but no corpus session had
exhibited. After the first long gap (364s) the log has `read 0` and a full
re-write (25,469 tokens) — the all-or-nothing lapse. After the next two gaps
(487s, 730s) it has `read 11,808` *and* a ~14k re-write: a stable prefix
breakpoint stayed warm while the conversation tail lapsed. The WP-05
lengthening rule only restores a re-write when the request read nothing, so
the 1h counterfactual recovers the full lapse but not the two partial ones —
and 1h loses a session that, by the 1h run's numbers, it should win. That is
a modeling limit to revisit in the simulator (restore `min(write, warm −
read)` on partial lapses, or similar); until then the tool under-sells 1h on
5m-configured sessions with partial lapses, which is the opposite direction
from the §7 conservatism disclosed in the UI. The golden pins today's
behavior so the change, when made, is visible.

### Scrubbing

`scripts/scrub-capture.py` keeps the exact row structure and every field the
engine reads, and replaces everything else. Concretely: numbers, booleans and
nulls survive everywhere; strings survive only under an allowlist of metadata
keys (record type, uuids, timestamps, model, version, effort, service tier,
speed, small enums); `message.content` becomes one placeholder block; `cwd` is
rewritten to `~/…`; the session title is replaced. The placeholder carries the
`POISON` marker, so the harness's content-poison check covers captures too.
After scrubbing, the only strings left are ids, timestamps, enums, the model
id, the version, `~/Code/cache-ttl-analyzer` and branch names — verified by
listing every distinct surviving string value before committing.

## Golden format

```jsonc
{
  "$schema": "cache-ttl-analyzer/golden/v1",
  "fixture": "synthetic/dedup-content-blocks",
  "outcome": "analysis",              // or "rejected", with { reason, stats }
  "metadata": { ... },                // SessionMetadata minus fileName/fileSizeBytes
  "parseStats": { ... },
  "parseWarnings": [ ... ],
  "buckets": [ { ...BucketAnalysis, including both scenarios' full event lists } ],
  "unknownModels": { ... }
}
```

It is the engine's `AnalysisResult` (see `src/engine/contract.ts`) minus the
inputs and config echoes (`fileName`, `fileSizeBytes`, `pricesAsOf`,
`approximation`).

## Assumptions recorded here

- **`inference_geo`** is not modeled. Requests with `inference_geo: "us"` (the
  1.1× data-residency rate) are priced at the standard published rate; the
  `synthetic/inference-geo-us` golden pins that behavior. Revisit if the
  contract grows an `inferenceGeo` field (docs/PLAN.md WP-04 notes).
