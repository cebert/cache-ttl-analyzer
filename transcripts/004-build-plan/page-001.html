3	
4	Upload Claude Code session logs in files (JSON or JSONL), and this tool will analyze whether you could save money by paying for a longer cache window duration.
5	
6	**Status:** scaffolding — nothing implemented yet. See [docs/PLAN.md](docs/PLAN.md).
7	
8	**Live URL:**  _not deployed yet (Cloudflare, planned)_

10	## Why
11	
12	[Prompt caching](https://code.claude.com/docs/en/prompt-caching) plays a critical role in agentic harnesses like Claude Code. Without caching, every turn must be reprocessed, which increases latency and cost.
13	
14	This tool was created to help answer the question: **should I pay for longer cache windows?**
15	
16	Claude Code picks a cache TTL for you, but the default depends on your plan. On a Claude subscription plan, the main conversation is cached for one hour under plan usage (usage credit usage drops to 5 minutes). When using an API key or a cloud provider like Amazon Bedrock, the default TTL is only five minutes. Users who aren't on a subscription plan must decide whether paying for longer caching (which incurs extra cost) is more economical than staying with shorter window durations. 
17	
18	Many excellent tools are already available to trace and review coding harness sessions, such as [Datadog Lapdog](https://chrisebert.net/see-what-your-ai-coding-agent-is-doing-with-datadog-lapdog/) and [Agents View](https://www.agentsview.io/).  However, these tools arguably focus less on prompt caching and seem to assume users are on subscription plans. 
19	
20	The organization I work for is increasingly concerned about AI costs and ensuring the value delivered matches or exceeds token costs. Like many other organizations, we are on a legacy Claude Code Enterprise Subscription plan with subsidized tokens that ends soon. Our organization is planning for the increased costs it will incur when it transitions to API-based billing in Amazon Bedrock or another provider with usage-based billing. Caching is one lever we can use to control costs, but few tools help us focus on this problem. The cache TTL analyzer can help with making these decisions. 
21	
22	From my experience, many developers are still unaware of the cost impact their behaviors have on caching. For example, changing effort or models mid-session will invalidate the cache, and resuming long-lived sessions can result in expensive cache misses. A secondary goal of this tool is to raise awareness of the cost impact of these behaviors.

1	# Feasibility: computing cache-TTL cost counterfactuals from Claude Code session logs
2	
3	**Date:** 2026-08-30
4	**Question:** Do Claude Code session logs contain enough data to recompute what a
5	session would have cost under a different `promptCacheTtl` (5m vs 1h), using
6	Anthropic's published API rates?
7	
8	**Verdict: Yes — build it.** Every input the cost model needs is present per
9	request. The exact-dollar *actual* cost is fully determined by the logs; the
10	*counterfactual* is a simulation with one honest approximation, described below.
11	
12	Two things the official docs added that reshape the product, both detailed later:
13	there are **two TTL settings**, not one (`promptCacheTtl` and
14	`subagentPromptCacheTtl`), so the tool should report two recommendations; and the
15	**defaults depend on how the user is billed**, which determines whether the dollar
16	figure is their real bill or a notional at-API-rates comparison. The one standing
17	risk is that Anthropic documents the file format as internal and unstable (§4).
18	
19	A working prototype (`prototype-sim.py`, alongside this doc) ran over 7 real
20	sessions end-to-end and produced differentiated recommendations, so this is
21	confirmed by execution, not by reading the schema.
22	
23	---
24	
25	## 1. Where the logs live and what they are
26	
27	[Officially](https://code.claude.com/docs/en/sessions#where-transcripts-are-stored):
28	`~/.claude/projects/<project>/<session-id>.jsonl`, where `<project>` is the working
29	directory path with non-alphanumeric characters replaced by `-` (truncated to 200
30	chars plus a hash of the full path when longer). `CLAUDE_CONFIG_DIR` can move the
31	root and `CLAUDE_CODE_PROJECT_DIR_NAME` can override the `<project>` segment, so an
32	uploader must not assume the path encodes a real directory. Transcripts are cleaned
33	up after 30 days by default (`cleanupPeriodDays`), which caps how much history any
34	user can bring.
35	
36	One JSON object per line. Record `type` values observed: `assistant`, `user`, `attachment`, `system`,
37	`file-history-snapshot`, `file-history-delta`, `mode`, `permission-mode`,
38	`bridge-session`, `ai-title`, `atis-latch`, `last-prompt`, `queue-operation`.
39	
40	**Only `type: "assistant"` rows carry billing data.** Everything else is ignorable
41	for this tool.
42	
43	## 2. The billing payload
44	
45	Every assistant row has `message.usage`:
46	
47	```json
48	{
49	  "input_tokens": 2,
50	  "cache_creation_input_tokens": 13185,
51	  "cache_read_input_tokens": 23472,
52	  "output_tokens": 386,
53	  "output_tokens_details": { "thinking_tokens": 237 },
54	  "cache_creation": {
55	    "ephemeral_5m_input_tokens": 0,
56	    "ephemeral_1h_input_tokens": 13185
57	  },
58	  "service_tier": "standard",
59	  "speed": "standard",
60	  "server_tool_use": { "web_search_requests": 0, "web_fetch_requests": 0 },
61	  "iterations": [ ... ]
62	}
63	```
64	
65	Plus on the row itself: `timestamp` (ISO-8601, ms), `requestId`, `message.id`,
66	`message.model`, `isSidechain`, `sessionId`, `cwd`, `gitBranch`, `version`.
67	
68	This is everything the cost model needs:
69	
70	| Needed | Field | Notes |
71	|---|---|---|
72	| Which model priced it | `message.model` | e.g. `claude-opus-5`, `claude-opus-4-8` |
73	| Uncached input | `usage.input_tokens` | |
74	| Cache reads | `usage.cache_read_input_tokens` | billed 0.1× base input |
75	| Cache writes | `usage.cache_creation_input_tokens` | |
76	| **Which TTL was actually used** | `usage.cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` | the decisive field |
77	| Output | `usage.output_tokens` | thinking tokens are already included |
78	| Request timing | `timestamp` on the assistant row; the preceding `user` row approximates request *start* | drives the expiry simulation |
79	| Rate modifiers | `usage.service_tier`, `usage.speed` | `speed: "fast"` on Opus 5 prices at $10/$50, not $5/$25 |
80	
81	**The configured `promptCacheTtl` value is not written to the log, and is not in
82	`settings.json` either.** It must be *inferred* from the `cache_creation` split.
83	That inference is reliable: in all 7 sessions on this machine, 100% of cache-write
84	tokens landed in `ephemeral_1h_input_tokens`, correctly identifying a 1h
85	configuration. Note the split is per-request, and a single request can legitimately
86	mix both TTLs (server tools insert their own 5m writes), so treat it as a
87	token-weighted mix, not a boolean.
88	
89	## 3. The setting being analyzed is actually two settings
90	
91	Anthropic documents [two independent TTL controls](https://code.claude.com/docs/en/prompt-caching#choose-the-ttl-yourself),
92	each accepting `5m` or `1h`, both requiring Claude Code **v2.1.242 or later**:
93	
94	| Bucket | Setting | Env var | Covers |
95	|---|---|---|---|
96	| Main conversation | [`promptCacheTtl`](https://code.claude.com/docs/en/settings-reference#promptcachettl) | `CLAUDE_CODE_PROMPT_CACHE_TTL` | interactive turns, `-p` runs, Agent SDK turns, inline helpers |
97	| Everything else | [`subagentPromptCacheTtl`](https://code.claude.com/docs/en/settings-reference#subagentpromptcachettl) | `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` | subagents, workflows, teammates, forks, compaction, session titles |
98	
99	**This makes the sidechain handling in §6.4 a product feature, not an edge case.**
100	The tool should report and recommend the two buckets separately — they are tuned
101	separately, they have different default values, and an agent-heavy workload can
102	easily want opposite answers for each.
103	
104	Resolution order when several controls apply (first match wins), per the docs:
105	`FORCE_PROMPT_CACHING_5M=1` → the bucket's env var → the bucket's setting →
106	a subagent's `experimental.cacheTtl` frontmatter (v2.1.248+) →
107	`ENABLE_PROMPT_CACHING_1H=1` → the bucket default.
108	
109	### What the log does and doesn't reveal about the setting
110	
111	**The configured value is never recorded.** No record type carries `promptCacheTtl`,
112	`subagentPromptCacheTtl`, either env var, or any settings snapshot — verified by
113	scanning every line of all 9 local session files for those names and for `"ttl"`.
114	The only hits are this project's own conversation content. The setting is also absent
115	from `settings.json`.
116	
117	What the log carries instead is the **effective TTL per request**, in
118	`usage.cache_creation`. That is arguably better than the setting: it is ground truth
119	*after* the entire six-step resolution order, so it already accounts for env vars,
120	managed settings, subagent frontmatter, and the plan-usage downgrade. But it answers
121	"what happened", never "what was configured" or "why".
122	
123	Two consequences:
124	
125	**Default vs. explicit is only inferable in one direction.** Comparing the two
126	buckets narrows the possibilities, but never confirms a default:
127	
128	| Observed pattern | What it means |
129	|---|---|
130	| Main 1h, subagents 5m | Consistent with subscription-within-plan defaults — but identical to an API-key user who set `promptCacheTtl: 1h` and left the other alone. **Ambiguous.** |
131	| Main 5m, subagents 5m | Consistent with API-key/credits defaults — or `FORCE_PROMPT_CACHING_5M=1`. **Ambiguous.** |
132	| Both 1h | No default combination produces this. Requires `ENABLE_PROMPT_CACHING_1H=1` or both settings set. **Definitely explicit.** |
133	| Main 5m, subagents 1h | No default produces this either. **Definitely explicit.** |
134	
135	So the tool can say "this was explicitly configured" with certainty in two of four
136	cases, and can never say "this was the default" with certainty. Billing mode is not
137	recoverable at all. Ask the user; don't guess.
138	
139	**The second bucket is mostly invisible.** Of the request classes
140	`subagentPromptCacheTtl` governs, only subagents appear in the transcript at all.
141	Verified: four sessions carry an `ai-title` record — proving a background
142	title-generation request ran — yet **no session contains a single Haiku-model
143	assistant row**. Helper and background requests are not written to the transcript
144	with usage. Compaction is unconfirmed either way, since no session in this corpus
145	compacted.
146	
147	Practically: unless the uploaded session ran subagents, the tool sees only the main
148	conversation bucket and can only advise on `promptCacheTtl`. It should say so rather
149	than implying it evaluated both.
150	
151	### Defaults depend on how you're billed — and this reframes the headline
152	
153	| Bucket | Claude subscription, within plan usage | Usage credits, API key, or cloud provider |
154	|---|---|---|
155	| Main conversation | **1 hour** | **5 minutes** |
156	| Everything else | 5 minutes (except server-controlled helpers) | 5 minutes |
157	
158	This explains the corpus cleanly: every local session wrote 1h because these ran on
159	a Claude subscription within plan usage, where 1h is the *default* — not because
160	anything was misconfigured. Two consequences worth stating plainly in the product:
161	
162	- **The framing "6 of 7 sessions were on the wrong setting" is about cost at API
163	  rates, not about a mistake anyone made.** For a subscription user inside plan
164	  usage there is no per-token bill at all, so the dollar figures are a *notional*
165	  "what this would have cost at published API rates" — exactly what was asked for,
166	  but it must be labelled as such or it will read as an invoice.
167	- **The audience that can act on the recommendation is the API-key / usage-credit /
168	  cloud-provider user**, who defaults to 5m on both buckets and may be leaving the
169	  1h win on the table for long, gap-heavy sessions. The tool cannot see billing mode
170	  in the log, so it should ask, or present both readings.
171	
172	## 4. The format is officially unstable — plan for it
173	
174	This is the one genuine project risk, and it comes straight from Anthropic:
175	
176	> Each line is a JSON object for a message, tool use, or metadata entry. **The entry
177	> format is internal to Claude Code and changes between versions, so scripts that
178	> parse these files directly can break on any release.** To build on session data,
179	> use `/export` or the script interfaces instead.
180	> — [Where transcripts are stored](https://code.claude.com/docs/en/sessions#where-transcripts-are-stored)
181	
182	The sanctioned alternatives don't serve this use case: `/export` renders prose for a
183	human and drops `usage` entirely, and the script interfaces
184	([`--output-format json`](https://code.claude.com/docs/en/headless#get-structured-output),
185	the [hook `transcript_path`](https://code.claude.com/docs/en/hooks#common-input-fields),
186	the Agent SDK) all cover a *live* run, not the historical sessions already sitting on
187	disk. Retrospective analysis has no supported path, so parsing the JSONL is the only
188	way to build this — which is a deliberate tradeoff, not an oversight to discover later.
189	
190	Mitigations, all cheap:
191	
192	- **Pin to the `version` field**, which every assistant row carries. Record the
193	  versions a build was validated against and warn on anything outside that range
194	  rather than failing silently. The corpus already spans 2.1.193 / 2.1.247 / 2.1.251.
195	- **Depend on the smallest possible surface.** The tool needs `type`, `timestamp`,
196	  `message.id`, `message.model`, `message.usage`, `isSidechain`, `effort`, `version` —
197	  eight fields. Never touch `message.content`. A narrow parser survives more releases
198	  and, per §9, is also the privacy-correct design.
199	- **Fail loudly and partially.** An unrecognized record type should be skipped and
200	  counted, not crash the run; surface "N records skipped" in the UI.
201	- **Ship fixtures** from each validated version so a format change shows up in CI
202	  rather than in a user's browser.
203	
204	## 5. The pricing math
205	
206	From Anthropic's published rates:
207	
208	- cache **read** = 0.1× the base input rate
209	- cache **write, 5m TTL** = 1.25× base input
210	- cache **write, 1h TTL** = 2.0× base input
211	- A cache read **refreshes the entry's timer at no cost**, on either TTL.
212	- Lifetime is measured from the **start** of the request that writes or reads it —
213	  generation time counts against the window.
214	
215	Base rates ($/1M): Opus 5 and Opus 4.8 $5/$25 · Sonnet 5 $2/$10 ·
216	Sonnet 4.6 $3/$15 · Haiku 4.5 $1/$5 · Fable 5 $10/$50.
217	
218	Break-even: 5m pays for itself at 2 requests (1.25 + 0.1 = 1.35 vs 2.0 uncached);
219	1h needs 3+ (2.0 + 0.2 = 2.2 vs 3.0). **1h only wins when gaps exceed 5 minutes** —
220	otherwise every request refreshes the 5m entry for free and the doubled write price
221	is pure loss. This is exactly the tradeoff the tool exists to quantify.
222	
223	## 6. Traps that will silently produce wrong numbers
224	
225	These are the reason a naive implementation gives garbage, and they're the real
226	value of this research.
227	
228	### 6.1 One JSONL row per content block — dedup is mandatory
229	
230	Claude Code writes **one row per content block of an assistant message**, and
231	**every one of those rows carries the full message `usage`**. Observed in real
232	logs: `msg_011CdygtRmd95FeRM1AqU7Xt` appears **13 times**, all with identical
233	`output_tokens: 12528`, `cache_read: 37044`. Summing rows overstates cost by up to
234	13×. Across the sample, 281 rows collapsed to 142 real requests.
235	
236	**Dedup on `message.id`.** Verified 1:1 with `requestId` across all 669 assistant
237	rows (0 requestIds mapping to >1 message id, and vice versa), so either key works.
238	
239	### 6.2 Synthetic rows
240	
241	`message.model == "<synthetic>"` rows exist (2 in the sample, from API error
242	paths). They have no `service_tier`/`speed` and represent no billable call.
243	Exclude them.
244	
245	### 6.3 Cross-file duplication
246	
247	`--resume` / fork can copy history into a new session file. Not observed in this
248	sample (0 message ids in >1 file), but if the tool accepts a folder upload,
249	dedup must be **global across files**, not per-file.
250	
251	### 6.4 Sidechains are a separate cache namespace
252	
253	`isSidechain: true` marks subagent turns. A subagent starts its own conversation
254	with its own system prompt and tool set, so its first request cannot read the
255	parent's cache and it warms one of its own. The simulator must partition by
256	`isSidechain` before computing gaps.
257	
258	Per §3 this is also the boundary of the second setting, `subagentPromptCacheTtl` —
259	so this is not merely a correctness detail but the split along which the tool
260	reports two separate recommendations. None appear in this sample, so **the path
261	is untested against real data until a session with subagents is captured.**
262	
263	### 6.5 Model and rate heterogeneity within one session
264	
265	The corpus spans `claude-opus-5` and `claude-opus-4-8`, though each individual
266	session held one model. Price per request anyway — a mid-session `/model` switch is
267	both legal and, per the docs below, a full cache invalidation. Also honor
268	`service_tier` (batch = 50%) and `speed` (fast mode = 2× on Opus 5).
269	
270	### 6.6 Model, effort, and version changes reset the cache entirely
271	
272	Per Anthropic's docs, the cache key includes the **model**, the **effort level**,
273	and the **fast-mode header** — and a Claude Code upgrade usually changes the system
274	prompt, invalidating from the top. All three are recoverable from the log: the row
275	carries `message.model`, `effort`, and `version`.
276	
277	The simulator must treat a change in any of them as a hard cache reset, independent
278	of elapsed time. In this corpus each session held one model, one effort, and one
279	version, so no in-session reset occurs — but `effort` does vary across sessions
280	(`high` vs `medium`) and `version` spans 2.1.193 / 2.1.247 / 2.1.251, so the fields
281	are live and the case is real.
282	
283	## 7. The one real approximation
284	
285	The actual cost is exact. The counterfactual is not, for one reason:
286	
287	**The logs report aggregate token counts, not per-breakpoint detail.** Claude Code
288	uses up to 4 cache breakpoints. When a 5m entry lapses, real-world behavior is a
289	*partial* invalidation — some breakpoints survive, some don't — but the logs only
290	give you a single `cache_read_input_tokens` total. The simulator therefore models
291	expiry as all-or-nothing: if the gap since the previous same-thread request exceeds
292	the TTL, the tokens that were read become a fresh write at the write multiplier.
293	
294	This **overstates** the penalty of the shorter TTL in mixed cases, which means the
295	5m recommendation is conservative — it will under-sell 5m rather than over-sell it.
296	That's the right direction to be wrong in, and it should be stated in the UI rather
297	than hidden.
298	
299	Second-order: `timestamp` on an assistant row is response completion, not request
300	start, and TTL runs from start. The preceding `user` row's timestamp is a good
301	proxy for start (observed ~2–5s earlier). Using it tightens gap accuracy; ignoring
302	it biases gaps slightly long. Cheap to do — do it.
303	
304	Third: sub-5-minute gaps that a 1h TTL would have covered are irrelevant, so the
305	simulation is only sensitive in the 5m–1h band. In this sample, only 1 session had
306	gaps in that band — which is also the only session where 1h won.
307	
308	Fourth, and newly confirmed from the docs: **cache scope is wider than one session.**
309	Claude Code's cache is effectively scoped to machine + working directory, so parallel
310	sessions in the same directory read each other's cache; a fork reads its parent's;
311	`/rewind` lands back on an already-warm entry; and the compaction request reads the
312	conversation prefix. A strictly per-session simulation therefore ignores real cross-
313	session hits. Treating each session independently is the right v1 — it is the unit
314	the user uploads and reasons about — but the folder-level rollup should not claim to
315	be exact, and cross-session sharing is a plausible v2 refinement.
