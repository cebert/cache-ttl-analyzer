### Input validation and secure file handling

The app is static and client-side, so the threat model is a malicious or
corrupted **file** being processed in the user's own browser — plus proving to
users that nothing is exfiltrated. Rules:

- **Three validation verdicts:** *valid*; *valid with warnings* (skipped
  records, out-of-range version, unknown model); or *not a session log* — no
  assistant rows carrying `usage`, or malformed-line share above a threshold
  (~10%) — with a plain-language error, never a garbage analysis.
- **Numeric hygiene:** every usage field is checked finite and non-negative
  before pricing; bad rows are skipped and counted.
- **Log-derived strings are untrusted input.** Title, `cwd`, `gitBranch`,
  model IDs render only as text nodes (no `innerHTML` anywhere), length-clamped.
- **No raw JSON into app state.** The parser copies the needed fields into
  typed records and discards the parsed object — no spreading of parsed
  objects, which also neutralizes prototype-pollution keys (`__proto__`,
  `constructor`).
- **Resource limits:** file-size cap with a clear message; streaming parse
  with a per-line length cap so one giant line can't exhaust tab memory;
  analysis in a worker so the page stays responsive; cancel always available.
- **CSP as proof, not just promise:** deploy with a strict
  Content-Security-Policy (`default-src 'self'`; no external `connect-src`)
  so "your data never leaves the browser" is enforced by the platform and
  verifiable in devtools — and mention that in the privacy statement.
- **Nothing persisted:** the file is never written to storage; in-memory
  history keeps analysis results, not file bytes.

Both requirements are in the plan now (commit ed8cd87), and the artifact is republished at the same URL. What I added:

Validation — a new "Input validation and secure file handling" subsection in the Architecture section. Every upload resolves to one of three verdicts: valid, valid with warnings (skipped records, unknown version/model), or not a session log (no assistant rows with usage, or too many malformed lines) with a plain-language rejection instead of a garbage analysis. Numeric fields are checked finite and non-negative before any pricing math. WP-07 gets these as distinct UI states.

Secure file handling — the threat model here is specific: with no backend, the risk is a malicious or corrupted file processed in the user's own browser. So: log-derived strings (title, cwd, branch, model IDs) are treated as untrusted and rendered only as text nodes; the parser copies fields into typed records and discards the raw parsed objects (which also neutralizes prototype-pollution keys); file-size and per-line length caps prevent memory exhaustion; and the deploy ships a strict Content-Security-Policy with no external connect-src — which doubles as proof of the privacy claim, since anyone can open devtools and see the platform itself forbids network egress. WP-03 and WP-06 now require adversarial tests and fixtures (hostile strings, pollution keys, giant lines, non-session files), WP-09 serves the CSP headers, and the risk table has a matching row.

On Zod — good instinct, and I've recorded it as a WP-03 investigation rather than a commitment: Zod 4.5's compilation feature is worth benchmarking, but this parser sits in a hot path validating potentially millions of lines, so the plan says adopt it only if it holds up against hand-rolled guards on the 100MB fixture. The validation rules are the requirement; the library is an implementation choice for that session to make with data.
