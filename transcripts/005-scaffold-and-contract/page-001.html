75	
76	- **Stack:** React + TypeScript + Vite. Deployed as **static assets on
77	  Cloudflare Workers** via Wrangler. **No server-side code in the MVP** — this

87	    feeds a session whose content blocks are poison values and asserts they
88	    never appear in any output (feasibility doc §9). One deliberate, named
89	    exception: the `ai-title` record (the short session title Claude Code
90	    generates), read for the session identification card (§3) — a single
91	    string, not conversation content. Not every session has one (4 of 7 in
92	    the research corpus); payload shape to be verified in WP-03.
93	  - **Simulator** implements the counterfactual model from the feasibility
94	    doc: see §3 below.
95	- **Web Worker** wraps the engine: streams the file
96	  (`File.stream()` + line splitting, so large logs don't need one giant
97	  string), posts progress messages, and supports cancellation (terminate).
98	- **Pricing config** (`src/config/pricing.json`): per-model base rates, cache
99	  multipliers (read 0.1×, 5m write 1.25×, 1h write 2.0×), `service_tier` and
100	  `speed` modifiers, and a top-level `pricesAsOf` date shown in the UI.

102	  policy: unpriced requests are excluded and disclosed, their share measured
103	  in **total tokens (input + cache + output) across deduped requests**, and
104	  the verdict is suppressed when that share exceeds **10%** (both the metric
105	  and the constant are named in the WP-02 contract so verdicts are
106	  deterministic).
107	- **UI** consumes a frozen engine contract (WP-02) so UI and engine work can
108	  proceed in parallel.
109	- **Logging** goes through a small leveled abstraction (`loglevel`, `tslog`,
110	  or a thin wrapper — chosen in WP-01), used everywhere including the worker
111	  (worker log events forwarded to the main thread). Quiet by default in
112	  production; a debug flag (query param or `localStorage` toggle, documented

115	  log collection would contradict the CSP/privacy stance. Anything the user
116	  needs to act on (skipped records, warnings) still surfaces in the UI, not
117	  just the log.

119	### Input validation and secure file handling
120	
121	The app is static and client-side, so the threat model is a malicious or
122	corrupted **file** being processed in the user's own browser — plus proving to
123	users that nothing is exfiltrated. Rules:
124	
125	- **Three validation verdicts:** *valid*; *valid with warnings* (skipped
126	  records, out-of-range version, unknown model); or *not a session log* — no
127	  assistant rows carrying `usage`, or malformed lines exceeding **10% of
128	  non-empty lines** (an exact named constant in the WP-02 contract) — with a
129	  plain-language error, never a garbage analysis.
130	- **Numeric hygiene:** every usage field is checked finite and non-negative
131	  before pricing; bad rows are skipped and counted.
132	- **Log-derived strings are untrusted input.** Title, `cwd`, `gitBranch`,
133	  model IDs render only as text nodes (no `innerHTML` anywhere), length-clamped.
134	- **No raw JSON into app state.** The parser copies the needed fields into
135	  typed records and discards the parsed object — no spreading of parsed
136	  objects, which also neutralizes prototype-pollution keys (`__proto__`,
137	  `constructor`).
138	- **Resource limits:** file-size cap with a clear message; streaming parse
139	  with a per-line length cap so one giant line can't exhaust tab memory;
140	  analysis in a worker so the page stays responsive; cancel always available.
141	- **CSP as proof, not just promise:** deploy with a strict
142	  Content-Security-Policy (`default-src 'self'`; no external `connect-src`)
143	  so "your data never leaves the browser" is enforced by the platform and
144	  verifiable in devtools — and mention that in the privacy statement.
145	- **Nothing persisted:** the file is never written to storage; in-memory
146	  history keeps analysis results, not file bytes.

177	bill; API-rate framing is what an API/Bedrock/credits user pays and what
178	everyone should understand — see decision log).

181	for the **subagent bucket** (`subagentPromptCacheTtl`), with its own
182	recommendation. When no sidechains exist, this section does not appear, and
183	the tool does not imply it evaluated subagent traffic (feasibility doc §3).
184	
185	**Insights (the educational layer):**
186	
187	- Timeline of cache events: writes, warm reads, expiries (with the gap that
188	  caused each), hard resets (annotated with the cause: model switch, effort
189	  change, version upgrade).
190	- Counts: cache invalidations, warm-read requests, wasted-write tokens.
191	- Observed effective TTL per bucket, and whether the configuration was

193	  otherwise no claim about defaults.
194	- Session shape summary: request count, span, largest gap, share of gaps in

204	## 5. The pricing math
205	
206	From Anthropic's published rates:
207	
208	- cache **read** = 0.1× the base input rate
209	- cache **write, 5m TTL** = 1.25× base input
210	- cache **write, 1h TTL** = 2.0× base input
211	- A cache read **refreshes the entry's timer at no cost**, on either TTL.
212	- Lifetime is measured from the **start** of the request that writes or reads it —
213	  generation time counts against the window.
214	
215	Base rates ($/1M): Opus 5 and Opus 4.8 $5/$25 · Sonnet 5 $2/$10 ·
216	Sonnet 4.6 $3/$15 · Haiku 4.5 $1/$5 · Fable 5 $10/$50.
217	
218	Break-even: 5m pays for itself at 2 requests (1.25 + 0.1 = 1.35 vs 2.0 uncached);
219	1h needs 3+ (2.0 + 0.2 = 2.2 vs 3.0). **1h only wins when gaps exceed 5 minutes** —
220	otherwise every request refreshes the 5m entry for free and the doubled write price
221	is pure loss. This is exactly the tradeoff the tool exists to quantify.

223	## 6. Traps that will silently produce wrong numbers
224	
225	These are the reason a naive implementation gives garbage, and they're the real
226	value of this research.
227	
228	### 6.1 One JSONL row per content block — dedup is mandatory
229	
230	Claude Code writes **one row per content block of an assistant message**, and
231	**every one of those rows carries the full message `usage`**. Observed in real
232	logs: `msg_011CdygtRmd95FeRM1AqU7Xt` appears **13 times**, all with identical
233	`output_tokens: 12528`, `cache_read: 37044`. Summing rows overstates cost by up to
234	13×. Across the sample, 281 rows collapsed to 142 real requests.
235	
236	**Dedup on `message.id`.** Verified 1:1 with `requestId` across all 669 assistant
237	rows (0 requestIds mapping to >1 message id, and vice versa), so either key works.
238	
239	### 6.2 Synthetic rows
240	
241	`message.model == "<synthetic>"` rows exist (2 in the sample, from API error
242	paths). They have no `service_tier`/`speed` and represent no billable call.
243	Exclude them.
244	
245	### 6.3 Cross-file duplication
246	
247	`--resume` / fork can copy history into a new session file. Not observed in this
248	sample (0 message ids in >1 file), but if the tool accepts a folder upload,
249	dedup must be **global across files**, not per-file.
250	
251	### 6.4 Sidechains are a separate cache namespace
252	
253	`isSidechain: true` marks subagent turns. A subagent starts its own conversation
254	with its own system prompt and tool set, so its first request cannot read the
255	parent's cache and it warms one of its own. The simulator must partition by
256	`isSidechain` before computing gaps.
257	
258	Per §3 this is also the boundary of the second setting, `subagentPromptCacheTtl` —
259	so this is not merely a correctness detail but the split along which the tool
260	reports two separate recommendations. None appear in this sample, so **the path
261	is untested against real data until a session with subagents is captured.**
262	
263	### 6.5 Model and rate heterogeneity within one session
264	
265	The corpus spans `claude-opus-5` and `claude-opus-4-8`, though each individual
266	session held one model. Price per request anyway — a mid-session `/model` switch is
267	both legal and, per the docs below, a full cache invalidation. Also honor
268	`service_tier` (batch = 50%) and `speed` (fast mode = 2× on Opus 5).
269	
270	### 6.6 Model, effort, and version changes reset the cache entirely
271	
272	Per Anthropic's docs, the cache key includes the **model**, the **effort level**,
273	and the **fast-mode header** — and a Claude Code upgrade usually changes the system
274	prompt, invalidating from the top. All three are recoverable from the log: the row
275	carries `message.model`, `effort`, and `version`.
276	
277	The simulator must treat a change in any of them as a hard cache reset, independent
278	of elapsed time. In this corpus each session held one model, one effort, and one
279	version, so no in-session reset occurs — but `effort` does vary across sessions
280	(`high` vs `medium`) and `version` spans 2.1.193 / 2.1.247 / 2.1.251, so the fields
281	are live and the case is real.

283	## 7. The one real approximation
284	
285	The actual cost is exact. The counterfactual is not, for one reason:
286	
287	**The logs report aggregate token counts, not per-breakpoint detail.** Claude Code
288	uses up to 4 cache breakpoints. When a 5m entry lapses, real-world behavior is a
289	*partial* invalidation — some breakpoints survive, some don't — but the logs only
290	give you a single `cache_read_input_tokens` total. The simulator therefore models
291	expiry as all-or-nothing: if the gap since the previous same-thread request exceeds
292	the TTL, the tokens that were read become a fresh write at the write multiplier.
293	
294	This **overstates** the penalty of the shorter TTL in mixed cases, which means the
295	5m recommendation is conservative — it will under-sell 5m rather than over-sell it.
296	That's the right direction to be wrong in, and it should be stated in the UI rather
297	than hidden.
298	
299	Second-order: `timestamp` on an assistant row is response completion, not request
300	start, and TTL runs from start. The preceding `user` row's timestamp is a good
301	proxy for start (observed ~2–5s earlier). Using it tightens gap accuracy; ignoring
302	it biases gaps slightly long. Cheap to do — do it.
303	
304	Third: sub-5-minute gaps that a 1h TTL would have covered are irrelevant, so the
305	simulation is only sensitive in the 5m–1h band. In this sample, only 1 session had
306	gaps in that band — which is also the only session where 1h won.
307	
308	Fourth, and newly confirmed from the docs: **cache scope is wider than one session.**
309	Claude Code's cache is effectively scoped to machine + working directory, so parallel
310	sessions in the same directory read each other's cache; a fork reads its parent's;
311	`/rewind` lands back on an already-warm entry; and the compaction request reads the
312	conversation prefix. A strictly per-session simulation therefore ignores real cross-
313	session hits. Treating each session independently is the right v1 — it is the unit
314	the user uploads and reasons about — but the folder-level rollup should not claim to
315	be exact, and cross-session sharing is a plausible v2 refinement.

# cache-ttl-analyzer

Upload Claude Code session logs in files (JSON or JSONL), and this tool will analyze whether you could save money by paying for a longer cache window duration.

**Status:** scaffolding — nothing implemented yet. See [docs/PLAN.md](docs/PLAN.md).

**Live URL:**  _not deployed yet (Cloudflare, planned)_

## Why

[Prompt caching](https://code.claude.com/docs/en/prompt-caching) plays a critical role in agentic harnesses like Claude Code. Without caching, every turn must be reprocessed, which increases latency and cost.

This tool was created to help answer the question: **should I pay for longer cache windows?**

Claude Code picks a cache TTL for you, but the default depends on your plan. On a Claude subscription plan, the main conversation is cached for one hour under plan usage (usage credit usage drops to 5 minutes). When using an API key or a cloud provider like Amazon Bedrock, the default TTL is only five minutes. Users who aren't on a subscription plan must decide whether paying for longer caching (which incurs extra cost) is more economical than staying with shorter window durations. 

Many excellent tools are already available to trace and review coding harness sessions, such as [Datadog Lapdog](https://[REDACTED_USER].net/see-what-your-ai-coding-agent-is-doing-with-datadog-lapdog/) and [Agents View](https://www.agentsview.io/).  However, these tools arguably focus less on prompt caching and seem to assume users are on subscription plans. 

The organization I work for is increasingly concerned about AI costs and ensuring the value delivered matches or exceeds token costs. Like many other organizations, we are on a legacy Claude Code Enterprise Subscription plan with subsidized tokens that ends soon. Our organization is planning for the increased costs it will incur when it transitions to API-based billing in Amazon Bedrock or another provider with usage-based billing. Caching is one lever we can use to control costs, but few tools help us focus on this problem. The cache TTL analyzer can help with making these decisions. 

From my experience, many developers are still unaware of the cost impact their behaviors have on caching. For example, changing effort or models mid-session will invalidate the cache, and resuming long-lived sessions can result in expensive cache misses. A secondary goal of this tool is to raise awareness of the cost impact of these behaviors.
